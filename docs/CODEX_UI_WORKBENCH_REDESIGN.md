## 画面構造

1. /dealsを案件一覧の直接入口にする。取引先は絞込。上段は「自分の担当」「営業対応」「期限」「情報不足」の絞込と検索。営業対応と個人担当は別概念とし、waiting_on=usだけで自分の担当と判定しない。
2. 一覧は1案件1行。案件名/取引先、文字付き現在工程、具体的な待ち先、担当、納期、採用額または未採用、作業入口。商品階層と列幅調整は詳細用の高度表示に分離。未設定案件も個別に表示する。
3. 行クリックは全幅の案件詳細を基本とし、簡易パネルは明示的な補助操作。パネルには要約・期限・不足・作業を開く1CTAだけを置く。RFQ作成や入金確定を常設しない。
4. 詳細の上部は案件名、現在工程、担当/納期、実データから決まる次の作業1つ。説明は短い不足理由、補足は折り畳み。Wasabiは主操作に集中。
5. 工程ナビは文字付きの閲覧専用。ステータス変更は該当作業面で明示確認と既存サーバー条件を通す。工程を開く操作と業務状態を変える操作を分ける。
6. 見積確定でも採用0件なら「採用見積を確認」を案内し、請求書新規発行を主操作にしない。既存帳票の閲覧/再発行は別入口で保持。旧仕様の欠損は推測補完しない。

## 改修・受入範囲

案件入口、簡易パネル、詳細ヘッダー、工程ナビ、共有next-action判定を先行。全routeの大きな説明枠・常設ボタンは同じ基準で整理する。DB/RLS変更・新業務機能を混ぜない。

状態fixture: 見積中(仕様なし/回答待ち/未採用/採用済み)、見積確定かつ採用0、請求書あり/なし、旧見積未紐付け、担当/納期/取引先なし、物流待ち、納品済み。各状態で表示CTAと実行可否を照合。

行動受入: 入口から対象案件と必要作業が分かる、パネルを閉じられる、工程閲覧が状態更新しない、案件詳細から絞込一覧へ戻れる、390/1280pxで操作・文字が読める。改善前後は同じ状態で撮影。クリック数は実測してから記録。対象テスト・lint/typecheck/build後に公開判断。

既存テスト合格はこの再設計の合格証拠にはしない。独立UX設計の受領後に統合する。

## 独立UXレビュー統合：実装する画面骨格

### 一覧（/deals）

上段: 案件管理 / 新規案件。次段: 要対応・進行中（既定）・すべて・完了の切替、検索、取引先filter。案件名・番号・顧客で直接検索。期限超過を先頭、次に本人担当かつ営業対応、残りは期限と更新順。納期は「希望納期」と明記し、請求支払期限と混同しない。

本体: 案件名＋番号 / 取引先 / 文字付き進捗 / 次の対応＋誰待ち / 希望納期 / 採用額税込 / 担当。案件名は全幅詳細へ、補助の「概要」で読み取りパネル。取引先未設定も個々の行に残す。商品階層編集と列リセット・全展開は補助メニュー配下。狭い画面は同じ情報優先度の案件カードにする。

集計: 採用なし、採用済み金額未登録、登録済み0円を区別。合計には金額未登録の件数も併記し、欠損を0円に変換しない。

### 詳細（/deals/:id）

上段: 条件を保持した一覧へ戻る / 案件名・番号・取引先 / 編集（補助）。その下に現在工程、担当、希望納期、採用額。次の対応は1行＋現在実行可能な主CTA1つ。待ち先のusは「営業対応」と表示し、担当本人と同義にしない。

主領域は該当工程の仕様・見積・請求書等。履歴・通信・添付は補助タブ。工程ナビは文字付き閲覧専用。過去工程の閲覧を選んでも「現在の工程」を書き換えない。状態を根拠に過去工程の実データが揃っていると判定しない。

請求の主操作: 採用なし→採用見積を確認、金額不足→金額を確認、発行なし→請求書を作成、発行あり→請求書を確認。送付・入金の事実を確認できないときに「送付済」「入金済」と表示しない。現documents照会には送付事実が含まれず、待ち先やsimple_statusは送付証拠ではないため、まず確認・手動送付記録の既存導線を示す。UIだけで新たな下書き/送付台帳や実入金機能を追加しない。入金状態変更は既存RPCの権限・条件を維持し、請求未作成時には主CTAにしない。

### 戻る・キーボード・状態検証

検索/切替/取引先はURLへ保持、一覧スクロールは非秘密のブラウザ内位置情報のみ保持。戻るで同じ案件行の位置とfocusを復元する。1366px/390px、キーボードの検索→行→詳細→戻るとフォーカス表示を確認する。

受入は「対象案件を直接探せる」「工程・次操作・待ち先・金額が詳細上部に見える」「請求作成が必要な場面で入金完了より強い」「閲覧で状態不変」「戻り条件と位置保持」を行動で検証する。「初見10秒」は人間テスト未実施のため達成を主張しない。

着手順: shared next-action/amount判定→直接案件一覧→readonly概要→詳細上部と主操作→既存他画面の競合する説明/CTA整理→状態fixture・journey・lint/typecheck/build。DB/migration/権限追加なし。

## 設計相談中：業務の一本の流れと現実装の境界

ユーザー合意待ち。構造再設計のコード実装・公開を先行しない。

本道: 案件一覧の要対応 → 案件を開く → 顧客・商品・数量・希望納期 → 仕様を確認 → 工場へRFQ → 回答比較・売値決定・採用 → 顧客へ見積提示 → 顧客承認 → 合意した取引条件に沿う請求・入金確認 → 工場発注・入稿確認・製造 → 輸送・検品 → 直接納品または倉庫入庫。

倉庫入庫後は同じ製造案件を「未完了」のまま毎月進める一本線にしない。商品在庫について「保管 → 顧客の出荷依頼 → 営業承認 → 物流出庫・配送 → 納品」を反復し、顧客・月単位で保管/入出庫料請求 → 送付結果確認 → 入金確認を並行管理する。製造案件の納品ステータスと残在庫・月次請求の完了を分離して表示する。

| 分岐・例外 | 現コードで確認した境界 | 設計上の扱い |
| --- | --- | --- |
| 前払/後払/半金 | 要件には取引条件があるが、現在のsimple_statusはquote_confirmed→paid→data_confirmedの固定順。UI改善だけで後払経路を成立したと扱えない | 合意条件を確認する作業として示す。固定順に合わない後払の扱いは別途決め、既存RPCを迂回しない |
| 工場支払と顧客入金 | 別の業務事実。現factory_purchase_ordersの公開型はordered/cancelledで、顧客paidから工場支払済を推定できない | 「工場発注」「工場への支払確認」を混同しない。未実装の支払管理を完了表示しない |
| 分割入庫 | createInboundForFactoryOrderはquantity入力を受け、累計数量は原子RPCで保護 | 入庫予定・受領を単位別に示す。1回の入庫で残り全量完了と表示しない |
| 継続在庫・分割出庫 | 顧客の出荷依頼と倉庫操作は独立し、在庫を繰り返し消費する | 案件詳細から在庫の該当商品/出荷へ。製造案件の完了と在庫ゼロは同一条件にしない |
| 月次保管請求 | client_id/billing_monthで発行。契約・倉庫根拠を営業が確認する入力、保管料＋入出庫回数単価。取引先・月の重複発行を拒否 | 顧客・月の別ワークスペース。日次在庫から正確な月中平均を自動取得できると主張しない |
| 出荷請求 | 保管請求には入出庫料があるが、配送運賃等の包括的な月次出荷請求の実装は今回確認できていない | 「出荷請求まで完成」と言わない。既存の請求対象範囲を明記し、新機能をUI修正に混ぜない |
| 送付・入金 | storage請求のemail_statusはattempting/accepted/unknown/rejected。acceptedは配信API受付で到達証拠ではない。今回コード照合で保管請求入金記録の完成までは確認していない | 発行・送付受付・到達・入金を別表示。未知は確認待ちとし、実際に記録できる作業だけCTAにする |
| 旧見積 | 状態見積確定でも採用なし、仕様未紐付け等がある | 元資料確認・既存帳票閲覧を保持。状態に合わせて採用や金額を補完しない |

画面遷移は「案件一覧 → 案件作業画面 → 選んだ工程」を基本にし、在庫や月次請求へ進んだ場合も案件/顧客へ戻る文脈を表示する。次の主操作は実行可能性・不足・待ち先から選ぶ。外部待ちなら無理に業務を進める主操作を作らず、対象依頼や連絡履歴の確認を示す。
